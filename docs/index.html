DBO regulated data store

Open source · MIT · Pre-1.0

A store for data somebody will one day audit.

DBO holds regulated records for organisations that do not trust each other, and the operator running it cannot read them.

Every disclosure is recorded and says why it happened. Every version is kept and cannot be quietly changed. Erasing a person is an operation that answers with a receipt. None of that is a policy somebody promises to honour. It is a set of things the operator cannot do.

Why another one of these

A clinical server stores clinical data. That is the easy half.

The questions that decide whether you may operate are different ones. Who read this record, and for what stated purpose. Can this person be erased, and can you show that it happened. Has this history been altered since it was written. Which organisation does this belong to, and what does its jurisdiction require. How long may it be kept.

Platforms answer those by hand, once per application, above a store that cannot help. The answers end up scattered across application code, where each one is somebody's good intention rather than a property of the system.

DBO is the store that helps. Its concepts are regulatory rather than clinical — object, identity, custody, declared handling, history, tenancy, erasure — and not one of them mentions medicine. A face maps a standard onto those concepts. Configure the FHIR face and you have a FHIR server, with the versions and the searches and the operations a client expects. Configure a different face and the same engine serves a domain that has never heard of a patient.

Properties, not policies

The difference between what an operator promises and what it cannot do.

A policy is a commitment somebody can break, forget, or be compelled to set aside. A property is something the system does not permit. Everything below is the second kind, and each one is proven by a test that runs on every commit.

A tenant is a database

Not a filter over a shared table that one wrong query defeats. Each organisation gets its own database with its own credentials. Erasing a tenant drops that database, rather than running a delete sweep somebody has to trust was complete.

The operator cannot read what it hosts

Provisioning hands the store a connection and never credentials. Each tenant is its own login authority, so the store accepts nobody else's tokens and a token from one tenant dies at another's signature check. Backups are sealed under the owner's key.

Erasure answers with a receipt

Erasing a person is asked for as work and answered by a run: what was found, how far it got, when. Asking twice is safe. A person the store never held is an answer rather than an error. A partial erasure is visible as exactly that.

Identifying data is encrypted where it lives

Identifying elements are encrypted inside the record itself, under a key held per person. History, backups, feeds and copies therefore carry ciphertext by construction rather than by somebody remembering. Erasure destroys a key instead of chasing copies, and a backup taken beforehand cannot resurrect the person.

Every disclosure says why

Reading identifying data requires a stated purpose. Without one, the record comes back with those fields omitted rather than filled in silently. The trail is append-only against everyone, the vendor included: an application says what happened, and the machinery stamps who and when from the credential and its clock.

Nothing changes quietly

Every version is kept, and each links to the one before it, so a history edited underneath the store fails verification. A record and the notice of its change commit together, so nothing downstream reacts to a state that was rolled back.

A question it cannot answer honestly is refused

An unrecognised search is an error, not a silently broader result set. In a clinical system a wrong set of results is a safety problem rather than a compatibility one, so the store would rather say no than guess. What it does support, it declares.

Records remember which rules checked them

A record written in 2026 must still be readable in 2029, when the rule that shaped it has moved twice. Each one carries the version it was validated against, so the store can find what is still on the old shape, convert it, and refuse to serve what it cannot honestly read.

It holds the work, not only the data

What has to be done, who is entitled to do it, who holds it now, and what happened. Work can also leave the building sealed, so an outside specialist performs a step without being handed anything they were not meant to see, and the trail tells carrying something apart from opening it.

Who this is for

A complete system, and three different reasons to care about it.

Legal and data protection

  • Access, portability, restriction and erasure are ordinary operations over the same machinery, not projects somebody schedules per request.
  • Erasure produces a record of what happened, which a deletion never could.
  • The audit trail is append-only against every party, so it is evidence rather than a log somebody could have tidied.
  • Retention is declared, and the sweep that enforces it is itself recorded without keeping what it removed.
  • Where the law differs by jurisdiction, that difference is a declaration a zone holds as records, not a branch buried in code.

Administrators and operators

  • Provision a tenant without ever holding its credentials, so hosting somebody's data never means being able to read it.
  • Backup is export and restore is import, through the machinery ordinary data movement already uses, rather than a format-specific tool kept in step by hand.
  • A sealed archive can be verified on a laptop with no network and no account.
  • Upgrades ride the deployment, so there is no window during which the store is down because somebody is running a migration.
  • One PostgreSQL database per tenant and nothing else to operate. No broker, no cache tier, no shared state service.

Architects and engineers

  • Two FHIR versions coexist in one process over one database, with no difference in the engine between them.
  • Embed it in your own application or run it as a server. The same bundles do both.
  • Identity, grants, audit and process definitions are all ordinary records, so rotating a key or changing who may act is an ordinary write.
  • A change feed, subscriptions, a terminology server and a process engine are part of the store rather than services beside it.
  • Every promised behaviour has a requirement code and a named test that proves it.
Regulation

Built where European rules are the design input, not a later audit.

The mechanisms above line up with obligations a European controller already carries: erasure and the evidence that it happened, subject access and portability, restriction of processing, storage limitation, and an account of who accessed what and why. Isolation between organisations is structural, so a processor hosting several of them is not relying on its own query discipline to keep them apart.

Standards over invention at every external surface. Where a published standard solves a problem, the store uses it rather than a proprietary field: FHIR at the data surface, OpenID Connect and SMART for who may act, SCIM for provisioning people, and standard cryptography from the platform with no invented primitives.

What a component can honestly claim. Compliance belongs to a deployment and the organisation running it, never to a piece of software, and any vendor telling you otherwise is selling something. What a store can do is make the evidence exist by default and make the unsafe thing impossible rather than discouraged. That is the line this project tries to hold, and the specification says where it stops.

Honesty about status

Pre-1.0, and specific about what that means.

249behaviours proven by a named test
15specified and not yet built
119integration test classes
MITlicence, no open-core tier

Behaviour here is not described, it is claimed and proven. Each promise has a requirement code and the test that demonstrates it, and the tests are sentences about behaviour rather than about methods. Most of them are integration tests: a real PostgreSQL, a real container, the shipped distribution booted as a separate process, and a real Kubernetes API server for the part that provisions tenants. Nothing publishes and no image ships unless the whole suite passes on exactly that commit.

What is built and what is only specified is written down and kept honest, including the parts that are missing. The routing layer for very large deployments has no implementation at all. Blob storage, a shared-database tier and quotas are specified and not built. Version numbers stay below 1.0 until the surfaces a 1.0 would freeze stop moving.

Read the implementation status, which is the document to believe over any impression the rest gives, or the requirement catalogue for every promise and its proof.

Getting it

A container image, or a dependency.

Run the server

docker run -p 8090:8090 \
  ghcr.io/jengu-net/dbo-server:latest

Embed the engine

dependencies {
  implementation("cloud.jengu.dbo:dbo-core")
}

The images carry the operator, the server and the fleet reader, for both Intel and ARM. A tenant needs a PostgreSQL database and a declaration of the types it holds. Start with running it for what operating this actually involves, or the FHIR face if you know FHIR and nothing about this store.
